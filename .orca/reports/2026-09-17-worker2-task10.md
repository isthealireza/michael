## Which failure I optimised for, and why (in my own words)

The plan's Task 10 said "lowest threshold with zero false positives," copied
from `RETRIEVAL_MIN_SCORE`. I did not use that rule, and here is why, in my own
words rather than reciting the plan review's finding back.

`RETRIEVAL_MIN_SCORE` protects against a failure the reader cannot see: an
answer built on a corpus that does not actually cover the question, with no
marker on the page that anything went wrong. Zero false positives is the only
sane target there, because the alternative is that Michael states law it
cannot support and nothing catches it.

Clause similarity is not that shape. Both of its failure directions print
something the reader can see and evaluate:

- Set the threshold too low, and two clauses that merely share a subject (two
  different termination clauses, two different notices clauses) get paired and
  a diff is printed between them. That diff is a **lie dressed as an edit** —
  it says "this changed" about two things that were never versions of each
  other, and a reader skimming a long comparison report can believe it.
- Set the threshold too high, and a clause that really was edited gets
  reported as one clause REMOVED and a new one ADDED. That is more verbose,
  but every word of it is **true** — the old text is gone, the new text is
  present, the reader loses only the "clause X changed" framing, not any fact.

So I optimised for **maximising correct pairings**, and where ties existed I
resolved them toward the **higher** threshold, because at an equal error count
I would always rather have one more true-but-verbose ADDED+REMOVED pair than
one more wrong pairing printing a false edit. A wrong pairing can mislead a
reader about what happened in a negotiation; a missed pairing can only bore
them. I do not think the retrieval rule was wrong for retrieval — I think it
was imported here without asking whether silence was still the shape of the
failure, and it is not.

## A defect this measurement found — not mine to fix, escalating

**`src/michael/contracts.py:310`** calls
`difflib.SequenceMatcher(None, normalise(a.text), normalise(b.text)).ratio()`
with Python's default `autojunk=True`. For one real pair in my labelled set —
the DISPUTE RESOLUTION clause, edited only in two numbers ("10 Business Days"
→ "15", "20 Business Days" → "30") — that default heuristic returns **0.1692**
where the true similarity is **0.9925** (`autojunk=False`, same two strings,
verified directly). `autojunk` marks a character that recurs often enough in
a sequence 200+ characters long as "popular" and refuses to use it as a match
anchor; this clause is 266 characters after normalisation and its character
distribution triggers exactly that behaviour. Nothing in Task 10's brief asks
me to touch alignment logic, and I have not — this is a one-character keyword
argument in `align()`, which is Task 5/WORKER-3's code, not mine to edit under
this task's constraints.

This is worth escalating for three reasons. First, it is real production
behaviour, not a labelling artefact: the exact same call, on the exact same
text, runs today in `compare()`, so a lightly-edited long clause in a real
contract can be silently misreported as REMOVED+ADDED regardless of what
`SIMILARITY_THRESHOLD` is set to — no threshold fixes a similarity function
that returns 0.17 for a 99%-identical string. Second, it reproduces the
project's own recurring lesson from a different angle: the plan's Task 10
worked example compares short single-sentence toy clauses, which never cross
the ~200-character length where `autojunk` degrades, so a test built from that
example cannot see this failure — the same shape as the monotonic section
floor, the CAPS_CLAUSE title bug, and the `clause_id` dict collision. Third,
it does not change my recommended number: I confirmed with `autojunk=False`
on this same labelled set that the identical plateau (0.55–0.74, tie-broken to
0.74) becomes **fully clean — 29/29, 0 wrong, 0 missed** — so 0.74 is correct
either way, and fixing `autojunk` would only remove a known false negative,
not move the threshold.

**Recommendation for whoever owns `contracts.py`:** pass `autojunk=False` at
`src/michael/contracts.py:173` and `:310`. I have not made this change.
