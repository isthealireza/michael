# Which model handles client data — decision memo

**Status:** decision memo only. This document does not change any model,
provider or routing configuration. It exists so the owner can decide with
the facts in front of them; see the recommendation at the end, clearly
labelled as a recommendation and not a decision.

**Scope:** the three models that passed `bench/` — `deepseek/deepseek-v4-pro`
(currently selected), `anthropic/claude-sonnet-5`, `anthropic/claude-opus-5`.

## 1. The current data path

Traced from the code and config in this repo, not assumed.

**What leaves the container, and to whom.**

1. **The answering model call.** Hermes (`nousresearch/hermes-agent`,
   running as the `michael-hermes` container) receives the scenario text
   verbatim — including any client facts the user typed — and sends it,
   plus the running conversation, to whatever model `model.default` names
   in `hermes/config.yaml` (rendered from `hermes/config.template.yaml`;
   today `deepseek/deepseek-v4-pro`). That call goes to OpenRouter, which
   routes it to an upstream inference provider. **`draft_document`'s
   `facts` argument is generated by the model itself** from the
   conversation (`src/michael/tools.py:253`, `def draft_document(request,
   *, facts: dict[str, str] | None = None, ...)`), so any client fact that
   ends up in a draft was already visible to the model in this same
   OpenRouter call — there is no path where facts reach `draft_document`
   without first passing through the model.
2. **Tool calls (`classify_request`, `search_provisions`, `draft_document`,
   `validate_output`).** These run in-container, as a stdio MCP subprocess
   (`src/michael/mcp_server.py`) using the read-only Postgres role
   (`michael_ro`). `classify_request` is regex only (`src/michael/tools.py`)
   and reaches no network. `search_provisions` and `draft_document` read
   legislation text from the local Postgres corpus — that traffic never
   leaves the container. **Retrieved provisions are then handed back to the
   model** as the tool's return value, so their text re-enters the same
   OpenRouter call as context for the final answer. This is public
   legislation text, not client data, but it does transit the same
   OpenRouter → upstream-provider path on the way back.
3. **Embeddings.** `search_provisions`/`draft_document` embed the search
   query (derived from the request, so it can carry client facts) via
   `src/michael/embeddings.py`, which posts to
   `EMBEDDING_BASE_URL=https://openrouter.ai/api/v1` with
   `EMBEDDING_MODEL=openai/text-embedding-3-small`
   (`hermes/config.template.yaml`, `.env.example`). This is a **second,
   independent OpenRouter call**, separate from the answering-model call.
   OpenRouter currently lists two endpoints for this exact model id:
   `OpenAI` and `Azure` (`openrouter.ai/api/v1/models/openai/text-embedding-3-small/endpoints`,
   queried directly) — i.e. the query text goes to OpenAI or to
   Microsoft-hosted OpenAI infrastructure, depending on OpenRouter's
   routing at call time.
4. **The auxiliary lane** (context compression, vision, session-title
   generation) falls back to OpenRouter's
   `nvidia/nemotron-3-ultra-550b-a55b:free` when the main provider is
   unavailable (`hermes/config.template.yaml`, `auxiliary:` block). Context
   compression by its nature needs the conversation content to compress it,
   so this is a **third path** by which scenario/client-fact content can
   reach a fourth party (whichever provider serves that model) — this is
   an existing, already-deployed fact about the current architecture, not
   part of this decision; its own upstream-provider pool was not
   researched for this memo (out of scope: it is not one of the three
   shortlisted models).
5. **No direct, non-OpenRouter model credentials exist anywhere in this
   repo.** `grep -rni openrouter` (and separately, a search for any other
   provider API key) turns up exactly one model-serving credential:
   `OPENROUTER_API_KEY`. There is no `ANTHROPIC_API_KEY`, `DEEPSEEK_API_KEY`,
   or similar in `.env.example`, `hermes/config.template.yaml`, or
   `src/michael/config.py`.

**A gap in today's config, found while tracing this.** Hermes Agent's own
config schema is `model: {default, provider, base_url, api_mode}`
(`hermes-agent.nousresearch.com/docs/user-guide/configuring-models`) — but
`hermes/config.template.yaml`'s `model:` block sets only `default`, not
`provider`. Hermes has its own multi-backend catalog (OpenRouter, Nous
Portal, Anthropic direct, GMI Cloud, and others —
`hermes-agent.nousresearch.com/docs/integrations/providers`), and without an
explicit `provider: openrouter` pin, Hermes decides the backend from the
model id itself. README.md already documents one observed case of this
going wrong: `hermes -m anthropic/claude-sonnet-5` **resolves to provider
`gmi`** (GMI Cloud, a first-class Hermes backend with its own credentials —
confirmed against Hermes' provider list) **and fails with no credentials**
rather than silently succeeding elsewhere — but that is what *this specific*
model id happens to do; nothing in the template pins the *production*
model (`deepseek/deepseek-v4-pro`) to the OpenRouter backend either. Today
it evidently resolves there in practice (`bench/`'s cost accounting only
works if it does), but that rests on Hermes' current default resolution for
that one id, not on an explicit, reviewable config line. §3 below gives the
exact fix.

## 3. What OpenRouter provider routing can enforce

OpenRouter's own provider-preferences object supports (confirmed directly
from `openrouter.ai/docs/guides/routing/provider-selection` and
`openrouter.ai/docs/guides/features/zdr`):

- `only: [...]` — allowlist of provider slugs.
- `ignore: [...]` — denylist.
- `data_collection: "deny"` — routes only to providers that do not use
  requests for training (default is `"allow"`).
- `zdr: true` — routes only to zero-data-retention endpoints.
- `allow_fallbacks: false` — refuse the request rather than fail over to
  an un-pinned provider (default `true`).

Hermes Agent exposes a `provider_routing` block that mirrors this, with a
top-level default and a per-model override
(`hermes-agent.nousresearch.com/docs/user-guide/features/provider-routing`,
confirmed): `sort`, `only`, `ignore`, `order`, `require_parameters`,
`data_collection`, with per-model pins under `provider_routing.models.<id>`.
**I could not independently confirm from that page that `zdr` and
`allow_fallbacks` specifically pass through Hermes' `provider_routing`
block** (the fetched page listed the six keys above and did not show those
two) — **UNVERIFIED**; confirm against Hermes v2026.8.31's actual schema
(or ask Nous Research support) before relying on `zdr`/`allow_fallbacks` in
production. `only`/`data_collection` are confirmed both ends.

**Exact `hermes/config.template.yaml` changes for each option** (not
applied — this phase only describes them):

**(a) Prerequisite for all of the below — pin the backend to OpenRouter.**
Today's `model:` block has no `provider` key, so Hermes' own model-id
resolution — not OpenRouter's — decides where a request goes (§1). Add:

```yaml
model:
  default: deepseek/deepseek-v4-pro
  provider: openrouter   # ADD — see README.md "Pin the provider when
                         # overriding the model" and §1 above (the 'gmi'
                         # resolution case).
```

**(b) Provider allowlist**, e.g. pin the selected Claude model to
Anthropic's own infrastructure only, excluding the Azure/Bedrock/Vertex
venues:

```yaml
provider_routing:
  models:
    anthropic/claude-sonnet-5:
      only: ["anthropic"]
```

(For `deepseek/deepseek-v4-pro`, `only` would need to name one or more of
the 15 slugs in §2 — e.g. `["gmicloud"]` — trading the multi-provider
failover away for a single, vetted venue.)

**(c) Deny training use, account-or-model-wide:**

```yaml
provider_routing:
  data_collection: deny
```

**(d) Zero data retention** (per OpenRouter's documented field; confirm
Hermes passthrough first — see the UNVERIFIED note above):

```yaml
provider_routing:
  zdr: true
```

**(e) Disable fallbacks**, so a request fails closed instead of silently
moving to a provider outside the allowlist:

```yaml
provider_routing:
  allow_fallbacks: false
```

These combine: a production block might read `provider_routing: {models:
{<id>: {only: [...], data_collection: deny, allow_fallbacks: false}}}`.

## 4. Privacy Act APP 8 and legal professional privilege — relevance, not advice

Michael's own rule is that it never gives legal advice; this memo holds to
the same rule for Michael's own infrastructure.

**APP 8 (cross-border disclosure, Privacy Act 1988 (Cth), Schedule 1)**
is relevant because, per §1 and §2, a scenario containing personal
information (an employee's or applicant's name, contact details, or similar,
which "casual employment contract" prompts routinely will) leaves the
container and is disclosed to overseas recipients: OpenRouter (US), and
whichever upstream inference provider serves the configured model — which,
unpinned, may be in the US, Singapore, or the PRC depending on the model
(§2). APP 8.1 requires Palm Vision (as the APP entity) to take reasonable
steps to ensure an overseas recipient does not breach the APPs before
disclosing personal information to it, subject to the APP 8.2 exceptions
(e.g. reasonable belief the recipient is subject to a substantially similar
protection, or informed consent) and the APP 8.3 prescribed-country/scheme
carve-out
(`oaic.gov.au/privacy/australian-privacy-principles/australian-privacy-principles-guidelines/chapter-8-app-8-cross-border-disclosure-of-personal-information`;
statutory text at
`classic.austlii.edu.au/au/legis/cth/consol_act/pa1988108/sch1.html`).
Whether the current or any reconfigured routing satisfies APP 8 — what
counts as "reasonable steps" here, whether any exception applies, and
whether a provider's own no-training/retention commitment is sufficient —
is a question this memo surfaces and does not answer.

**Legal professional privilege** is relevant because some of what Michael
processes (research and drafting done for the dominant purpose of giving or
obtaining legal advice, or in relation to anticipated proceedings) may
attract privilege. Sending the underlying material to a third-party model
provider — which, per §2, may retain it for some period even under a
"no training" commitment (e.g. flagged-content retention up to 2 years even
under Anthropic's ZDR arrangement) — raises the question of whether that
disclosure is consistent with maintaining privilege, and separately,
whether the solicitors' professional-conduct duty of confidentiality is
being met. This memo does not conclude on either question; both are
squarely "get advice" items, consistent with Michael's own closing notice
on every output.

## 6. Recommendation

**Recommendation:** keep `deepseek/deepseek-v4-pro` for now, but treat §1's
missing `model.provider: openrouter` pin as a bug to fix immediately
regardless of what this decision becomes — it is a routing-integrity gap,
not a data-residency trade-off, and today's cost accounting in `bench/`
implicitly depends on it holding by accident. If the owner decides client
data warrants routing exclusively to a single, fully-vetted venue, pin
`anthropic/claude-sonnet-5` with `provider_routing.models.<id>.only:
["anthropic"]` (§3b) and re-run `bench/` with that exact pin (now possible —
see below) before switching, since §2 shows this is the only one of the
three shortlisted models where all upstream routes and their policies were
independently confirmed in this memo; `claude-opus-5` gets the same
guarantee for roughly 3.6× the cost with no rule-compliance advantage shown
in `bench/`, and `deepseek-v4-pro`'s cheapest, fully-vetted single-provider
pin was not established here (2 of its 15 possible venues are PRC-based,
and 13 of the 15 were not individually assessed — §2).

**Trade-off:** `deepseek/deepseek-v4-pro` is ~5× cheaper than
`claude-sonnet-5` and ~19× cheaper than `claude-opus-5` (§5), but pinning it
to a single fully-vetted provider was not established in this memo, so
today it either keeps the cheap price with an under-verified, 15-way
provider pool, or gives up that price advantage to reach the same
verification level as `claude-sonnet-5`. That is the owner's call, not
this memo's.

## Bench harness: provider pinning

`bench/run_bench.py` can now pin a shortlisted model to a specific
OpenRouter provider slug and re-run the benchmark with that exact routing,
so a decision made from §2/§3 above can be verified against production
routing before it ships — without touching `hermes/config.template.yaml`.

- **`PROVIDER_PINS: dict[str, str]`** — empty by default (unchanged
  behaviour for every existing model). Set e.g.
  `PROVIDER_PINS = {"anthropic/claude-sonnet-5": "anthropic"}` to pin one
  model.
- **`render_pinned_config(base_config_yaml, model, provider)`** — pure
  text-in/text-out: adds `provider_routing.models.<model>.only:
  [<provider>]` to a parsed copy of the config, preserving everything else
  (the model default, the MCP server block, disabled toolsets, ...)
  unchanged. No filesystem, no Hermes, no Docker — this is what the unit
  tests exercise directly.
- **`provider_pin_home(model, ...)`** — reads the container's real,
  already-rendered `/opt/data/config.yaml` (never writes to it), renders
  the pinned overlay, and writes it to a fresh temp directory. `main()`
  points `HERMES_HOME` at that directory for just the one `hermes`
  subprocess call (Hermes resolves its config from
  `${HERMES_HOME}/config.yaml`), then removes the directory afterwards.
  Every other model's call is unaffected.
- **`run_slug(model, provider, prompt_name, run)`** — a pinned run's
  filename/record carries the provider, so it lands beside the existing
  unpinned baseline for that model rather than overwriting or silently
  deduplicating against it; the JSONL record now also carries a
  `"provider"` field (`null` when unpinned, so `bench/analyse.py` and
  `bench/score_final.py`, which read fields by name, are unaffected).

**Tested** in `tests/test_run_bench.py` (8 tests, all passing; reaches
`bench/run_bench.py` the same way `bench/analyse.py` reaches `michael` — by
adding its directory to `sys.path`), covering: the config merge adds the
right `only` list and leaves the rest of the config untouched; an existing
pin for a different model is preserved when a second one is added; a
non-mapping base config is rejected; `provider_pin_home` returns `None`
when a model isn't pinned; it writes a correct overlay **without mutating
the base config file**; and `run_slug` is unchanged when unpinned but
carries the provider when pinned.
